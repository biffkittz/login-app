# Authentication: Azure, Cloudflare and the TLS certificate

Every credential the Terraform project uses, where it lives, and how to set it up. Nothing secret is stored in the
repository:

- Azure credentials come from the Azure CLI (or OIDC in CI).
- The Cloudflare token comes from an environment variable.
- The certificate comes from a file outside the repository.

## At a glance

| Credential | Used for | Lives in | Provided as |
| --- | --- | --- | --- |
| Your Azure identity (or a CI identity) | Every Azure API call, the state backend, `az acr build`, `az containerapp job start` | Azure CLI token cache (`~/.azure`) | `az login` (CI: OIDC, see below) |
| Cloudflare API token | Reading the zone and Cloudflare's IP ranges, managing the DNS records, Origin Rules and the Authenticated Origin Pulls setting, and, with registration emails, Cloudflare Email Service and the app's email token | Your password manager | `CLOUDFLARE_API_TOKEN` environment variable |
| Origin certificate PFX and its password | The app's HTTPS (Kestrel in the container) | A file outside the repo, e.g. `~/.secrets/biffkittz-origin.pfx` | `TF_VAR_tls_certificate_pfx_path`, `TF_VAR_tls_certificate_pfx_password` |
| Generated secrets (database passwords, JWT key) | The app and the bootstrap job | Key Vault (and the remote state) | Generated by Terraform; nobody handles them |
| The app's Cloudflare email token | Sending registration emails (Email Sending permission only) | Key Vault (and the remote state) | Created by Terraform as an account-owned token; nobody handles it |
| GitHub OAuth App's client secret (with observability) | Grafana's GitHub sign-in | Your password manager; Key Vault (and the remote state) | `TF_VAR_grafana_github_client_secret` (CI: `GRAFANA_GITHUB_CLIENT_SECRET`) |
| Prometheus' passwords, Grafana's secret key (with observability) | The app pushing metrics, Grafana querying them, Grafana's encryption | Key Vault (and the remote state) | Generated by Terraform; nobody handles them |
| Temporal Cloud API key (with grocery runs) | The app starting and signalling grocery run workflows, and its worker running them | Your password manager; Key Vault (and the remote state) | `TF_VAR_temporal_api_key` (CI: `TEMPORAL_API_KEY`) |

## Azure

### Sign in

Use the **Linux** Azure CLI inside WSL (see [DEVELOPMENT.md](DEVELOPMENT.md#1-install-the-tools)). The Windows CLI
also works through WSL interop, but it is slower and keeps its tokens on the Windows side.

```bash
az login                     # opens a browser; on a headless WSL use: az login --use-device-code
az account set --subscription 3c3f379f-8161-4631-a30c-a3af82622a6a
az account show --query "{subscription:name, id:id, user:user.name}" --output table
```

The azurerm provider and the azurerm state backend both pick up the CLI's token automatically. No client secret or
access key is involved, and `subscription_id` comes from `environments/demo.tfvars`. Tokens expire: if a plan fails
with `AADSTS700082` or "refresh token has expired", run `az login` again.

### Required permissions

| Scope | Role | Why |
| --- | --- | --- |
| Subscription | **Owner**, or **Contributor** + **Role Based Access Control Administrator** | Terraform creates resources *and* role assignments (AcrPull, Key Vault roles). Registering resource providers (`Microsoft.App`, …) also needs subscription-level rights |
| State storage account `demonstration` | See [Remote state](#remote-state) | Reading and writing `loginapp.terraform.tfstate` |

To keep Role Based Access Control Administrator narrow, add a condition that only allows the four roles this
configuration assigns: AcrPull, Key Vault Secrets User, Key Vault Secrets Officer and Key Vault Certificates Officer.
The portal's "Constrain roles" option builds that condition.

### What Terraform grants itself

Key Vault uses Azure RBAC, so even an Owner can't read or write secrets until a data-plane role is assigned.
The `key-vault` module grants the identity running Terraform two roles:

- **Key Vault Secrets Officer**;
- **Key Vault Certificates Officer**.

The identity is found with `data.azurerm_client_config.current.object_id`. The module then waits 90 seconds for the
assignment to propagate before creating secrets.

If someone else runs a later apply, Terraform gives the roles to them instead, because the principal ID changed. Once
more than one principal runs Terraform (you and CI), name them: `key_vault_administrator_object_id` for the main
one and `key_vault_additional_administrators` for the rest, so every one keeps the roles ([docs/CI_CD.md](../../docs/CI_CD.md#2-let-the-deploy-identity-manage-key-vaults-contents)).

### Remote state

`backend.tf` stores state in blob `loginapp.terraform.tfstate`, in container `terraform` of storage account
`demonstration` (resource group `rg-terraform-state`). The backend takes a **blob lease** for every operation that can
write state, so concurrent applies are refused with "Error acquiring the state lock".

**Current setting: storage key.** `use_azuread_auth` is commented out, so the backend looks up the storage account
key with your Azure CLI identity. That needs `Microsoft.Storage/storageAccounts/listKeys/action` on the account,
which Owner, Contributor and Storage Account Contributor include.

**Recommended: Microsoft Entra ID.** No shared keys:

1. Grant every operator and CI identity **Storage Blob Data Contributor** on the `terraform` container (or the account):

   ```bash
   az role assignment create --role "Storage Blob Data Contributor" --assignee "$(az ad signed-in-user show --query id -o tsv)" \
     --scope "$(az storage account show -n demonstration -g rg-terraform-state --query id -o tsv)/blobServices/default/containers/terraform"
   ```

2. Uncomment `use_azuread_auth = true` (and `use_cli = true`) in `backend.tf`, then run
   `terraform init -reconfigure`.
3. Optionally, disallow shared key access on the account:
   `az storage account update -n demonstration -g rg-terraform-state --allow-shared-key-access false`.

**Protect the state.** It holds the generated passwords, the JWT signing key and the PFX, all marked sensitive but
readable by anyone who can read the blob. Treat access to the state like access to Key Vault:

- keep the container private;
- limit who has data roles;
- keep versioning and soft delete on.

**A stuck lock.** If an apply was killed and left the lock behind, the next run reports the lock ID. Use
`terraform force-unlock <LOCK_ID>`, but only once you're sure nobody else is running.

### Pushing images and running the bootstrap job

- **`az acr build`** builds in the registry and needs push rights. Owner and Contributor have them through the
  registry's ARM permissions; otherwise grant **AcrPush** on the registry.
- **`az containerapp job start`** needs `Microsoft.App/jobs/start/action`, which Contributor includes.

Starting a job is a privileged action. The Jobs API accepts an execution template that can override the job's image
and command, so anyone who can start the job can read the secrets it references, including the PostgreSQL
administrator password. Microsoft calls this out in its secrets documentation. Grant the permission only to people
who may hold that password.

### CI/CD with OpenID Connect

GitHub Actions plans and applies with **OIDC workload identity federation**: no Azure secret is stored in GitHub. Three
user-assigned managed identities in `rg-terraform-state`, created by
[`scripts/setup-github-oidc.sh`](../scripts/setup-github-oidc.sh), each trust one or two GitHub environments:

| Identity | Environments | Roles |
| --- | --- | --- |
| `id-loginapp-github-plan` | `infra-pr` | Reader on the subscription; Storage Blob Data Reader on the state container |
| `id-loginapp-github-deploy` | `demo-plan`, `demo` | Contributor and constrained Role Based Access Control Administrator (it may grant only AcrPull, the Key Vault roles and Monitoring Reader) on the subscription; Storage Blob Data Contributor on the state container; Key Vault administrator through `key_vault_additional_administrators` |
| `id-loginapp-github-push` | `registry` | AcrPush and Reader on the registry |

CI passes `use_azuread_auth` and `use_oidc` to the backend with `-backend-config`, so `backend.tf` stays as it is for
local runs. The setup, the GitHub environments and their secrets are in [docs/CI_CD.md](../../docs/CI_CD.md).

## Cloudflare

### Create the API token

Use a scoped **API token**, not the account-wide Global API Key.

1. In the Cloudflare dashboard, open **My Profile → API Tokens → Create Token**, then pick the **Edit zone DNS**
   template.
2. Set **Permissions** to **Zone · DNS · Edit**, and add **Zone · Zone Settings · Edit** and **Zone · Origin Rules ·
   Edit**.
3. Under **Zone Resources**, choose **Include · Specific zone · biffkittz.com**.
4. For registration emails (`registration_notification_recipients`), add three **Account** permissions: **Email
   Sending · Edit**, **Email Routing Addresses · Edit** and **Account API Tokens · Edit**, and under **Account
   Resources** choose **Include · <the account that owns biffkittz.com>**. Email Sending must be **Edit** (Read
   can't onboard a domain), and it exists only as an Account permission, although onboarding is a call on the zone.
5. Optional but recommended:
   - **Client IP Address Filtering**: your public IP and CI's.
   - **TTL**: an expiry date, so a leaked token dies on its own.
6. Create it and copy the token once. Cloudflare doesn't show it again.

These permissions cover everything Terraform does:

- look up the zone ID for `biffkittz.com` (DNS Read is accepted for that);
- create, update and delete the single `app` A record;
- turn on Authenticated Origin Pulls (the `tls_client_auth` zone setting), so Cloudflare presents its client
  certificate to the origin;
- create the zone's Origin Rules ruleset with one rule that sends `app.biffkittz.com` traffic to the app's port
  (8443), because Azure keeps 443 on the environment for its own HTTP ingress;
- for registration emails: onboard biffkittz.com for Email Sending (Email Sending), add each recipient as a
  destination address of the account (Email Routing Addresses), and read Cloudflare's catalogue of token permissions
  and create the app's own token (Account API Tokens).

The app's email token is a separate, **account-owned** token that Terraform creates (module `email-sending`). It holds
only **Email Sending Write**, because Cloudflare has nothing narrower that can send: a leaked copy could send email
from biffkittz.com and change the account's Email Sending setup (remove the sending domain, say), but nothing else.
It belongs to no person's login, so it keeps working when your own token is rolled or deleted. Terraform writes it to
Key Vault (`Email--ApiToken`), which is the only place the app reads it from; rotating it is a `-replace`
([DEPLOYMENT.md](DEPLOYMENT.md#rotating-the-email-token)).

A token missing one of these fails on that step with a 403 and `Authentication error` (code 10000), except for Email
Sending: onboarding the domain then fails with `401 Unauthorized` and code 2036. Edit the token and add the
permission; editing keeps the token's value, so the exported `CLOUDFLARE_API_TOKEN` stays valid.

Reading Cloudflare's IP ranges uses a public endpoint and needs no permission.

### Use the token

The provider reads `CLOUDFLARE_API_TOKEN` from the environment. It is deliberately **not** a Terraform variable, so
it can't end up in a tfvars file, a plan file or the state.

```bash
read -rsp 'Cloudflare API token: ' CLOUDFLARE_API_TOKEN && export CLOUDFLARE_API_TOKEN && echo
# Optional check: prints "This API Token is valid and active"
curl -s -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" https://api.cloudflare.com/client/v4/user/tokens/verify \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["messages"][0]["message"])'
```

To rotate the token, use **Roll** on the token in the dashboard, then update your password manager and the CI
secret.

### Zone settings to check once

Terraform manages the instances' DNS records, the Origin Rules and Authenticated Origin Pulls (SSL/TLS → Origin Server). The settings below
affect every record in `biffkittz.com`, so set them in the dashboard:

| Setting | Value | Why |
| --- | --- | --- |
| SSL/TLS → Overview → encryption mode | **Full (strict)** | Cloudflare connects to the app over HTTPS and verifies the origin certificate. *Flexible* would use plain HTTP, which the app doesn't accept |
| SSL/TLS → Edge Certificates → Always Use HTTPS | On | Visitors who type `http://` are redirected at the edge |
| SSL/TLS → Edge Certificates → Minimum TLS Version | 1.2 | Matches the app's TLS 1.2+ setting |
| SSL/TLS → Edge Certificates → HSTS | Optional | Add it once HTTPS works end to end; it is hard to undo, because browsers cache it |
| Network → WebSockets | On (the default) | The grocery list's realtime updates are a WebSocket. With it off, the app falls back to reloading the list every 30 seconds |

## The origin certificate (PFX)

The app presents a **Cloudflare Origin CA** certificate. Cloudflare trusts it when validating the origin;
browsers don't, which is fine, because browsers only ever see Cloudflare's edge certificate.

1. **Create it.** In the dashboard for `biffkittz.com`, open **SSL/TLS → Origin Server → Create Certificate**:
   - **Generate private key and CSR with Cloudflare**, with an RSA (2048) key;
   - host names `*.biffkittz.com` and `biffkittz.com` (the wildcard covers every instance of the app:
     app.biffkittz.com, grocery.biffkittz.com and any added later);
   - a validity of up to 15 years.

   Copy the certificate into `origin.pem` and the private key into `origin.key`. The key is shown only once.

2. **Convert to PFX.** Terraform imports a PKCS#12 file with the private key into Key Vault (protect it with a
   password while it sits on disk):

   ```bash
   mkdir -p ~/.secrets && chmod 700 ~/.secrets
   read -rsp 'New PFX password: ' PFX_PASSWORD && export PFX_PASSWORD && echo
   openssl pkcs12 -export -inkey origin.key -in origin.pem \
     -out ~/.secrets/biffkittz-origin.pfx -passout env:PFX_PASSWORD
   chmod 600 ~/.secrets/biffkittz-origin.pfx
   shred -u origin.key            # the PFX now holds the key
   ```

   If you already have the wildcard PFX, just copy it to `~/.secrets/`. OpenSSL 3 encrypts PFX files with AES-256 by
   default. If Key Vault rejects the import with a password or format error, re-create the file with `-legacy`
   added to the `openssl pkcs12` command.

3. **Give it to Terraform** in the shell where you run it:

   ```bash
   export TF_VAR_tls_certificate_pfx_path=~/.secrets/biffkittz-origin.pfx
   export TF_VAR_tls_certificate_pfx_password="$PFX_PASSWORD"
   ```

Terraform imports the file into Key Vault as `app-biffkittz-com-origin`. Every plan reads the file, so keep it
available. Changing the file and applying imports a new version, and the app switches to it on its own (within 30
minutes; Container Apps restarts it). Key Vault hands the certificate to the app as a passwordless PFX. The repo's
`.gitignore` blocks `*.pfx`, `*.pem` and `*.key` as a safety net, but keep these files outside the repository
anyway.

## Grafana's GitHub sign-in

With `observability_enabled`, Grafana at https://grafana.biffkittz.com signs people in with GitHub and nothing else:
it has no login form, no basic authentication and no admin password. A GitHub **OAuth App** does the sign-in. Its
client ID starts with `Ov23li`; one starting with `Iv` belongs to a **GitHub App**, a different kind, whose tokens
take permissions instead of scopes and may not be allowed to list your teams, which Grafana does at every sign-in.

1. GitHub: **Settings → Developer settings → OAuth Apps → New OAuth App**. Homepage URL
   `https://grafana.biffkittz.com`; Authorization callback URL `https://grafana.biffkittz.com/login/github`.
2. Its **Client ID** goes in `grafana_github_client_id` (`environments/demo.tfvars`); it identifies the app and isn't
   a secret.
3. **Generate a new client secret** and keep it in your password manager. Pass it as
   `TF_VAR_grafana_github_client_secret`, and in CI as the `GRAFANA_GITHUB_CLIENT_SECRET` environment secret; Terraform
   keeps it in Key Vault (`grafana-github-client-secret`), where only Grafana's identity can read it.

Grafana asks GitHub for the `user:email` scope (to read a private email address) and `read:org` (Grafana lists your
teams at every sign-in, and GitHub allows that only with this scope); it can't write anything. Who gets in is decided
by username, not by organization:
`grafana_github_admins` become Grafana administrators, `grafana_github_viewers` may look, and everyone else is
refused after GitHub (Grafana's `role_attribute_strict`). Roles are re-read at every sign-in, so removing a username
and applying takes effect at that person's next sign-in; sessions last at most 7 days (2 without activity).

To rotate the client secret: generate a new one in the OAuth App, update `TF_VAR_grafana_github_client_secret` (and
the CI secret), apply, wait until Grafana has the new value (Container Apps re-reads Key Vault within 30 minutes and
restarts Grafana), then delete the old one in GitHub.

## Temporal Cloud

With `temporal_namespace` set, both sites run their grocery runs in that Temporal Cloud namespace, and connect with an
**API key** over TLS. The key belongs to a **namespace-scoped service account**, not to a person: it keeps working when
people come and go, and it reaches this one namespace only.

1. Temporal Cloud: **Namespaces → Create Namespace**. Choose **API key** authentication (a namespace created for API
   keys can't add mTLS later, nor needs it). For the region, Temporal Cloud has no Azure regions; AWS `us-east-2`
   (Ohio) is the nearest to Azure Central US. The namespace's full ID, `<namespace>.<account>` as the UI shows it, goes
   in `temporal_namespace` (`environments/demo.tfvars`); it isn't a secret.
2. The namespace's page: **Settings → Service accounts** (or the banner's **Generate API Key**). Create a
   namespace-scoped service account with **Write** permission (it starts workflows, signals them and runs a worker;
   it administers nothing), and an API key for it. Keys expire, after 2 years at most; pick a date you'll notice.
   The key is shown once: keep it in your password manager.
3. Pass it as `TF_VAR_temporal_api_key`, and in CI as the `TEMPORAL_API_KEY` environment secret (`infra-pr`,
   `demo-plan`). Terraform keeps it in Key Vault (`Temporal--ApiKey`), where only the app's identity can read it. A
   namespace without a key, or a key without a namespace, fails the plan.

```bash
read -rsp 'Temporal Cloud API key: ' TF_VAR_temporal_api_key && export TF_VAR_temporal_api_key && echo
```

The app sends only IDs and times to Temporal Cloud (see "Grocery runs" in [docs/ARCHITECTURE.md](../../docs/ARCHITECTURE.md#grocery-runs)),
so the namespace holds no names, email addresses or items.

To rotate the key, see [DEPLOYMENT.md](DEPLOYMENT.md#rotating-the-api-key): a service account can hold several keys
at once, so the new one goes in before the old one is deleted, and nothing stops.

## Handling secrets

**Do:**

- Keep the Cloudflare token, the PFX and its password in a password manager, and load them per shell session with
  `read -s` as shown above.
- Treat the remote state as secret, and use Entra ID authentication for it.
- Let workloads read secrets only from Key Vault, through their managed identities.

**Don't:**

- Commit any `*.tfvars` other than `environments/*.tfvars`, and never put a secret in those.
- Pass secrets with `-var` on the command line: they end up in shell history.
- Share saved plan files (`*.tfplan`). They contain the same secrets as the state, and `.gitignore` excludes them.
