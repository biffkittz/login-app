# Authentication: Azure, Cloudflare and the TLS certificate

Every credential the Terraform project uses, where it lives, and how to set it up. Nothing secret is stored in the
repository:

- Azure credentials come from the Azure CLI (or OIDC in CI).
- The Cloudflare token comes from an environment variable.
- The certificate comes from a file outside the repository.

## At a glance

| Credential | Used for | Lives in | Provided as |
| --- | --- | --- | --- |
| Your Azure identity (or a CI identity) | Every Azure API call, the state backend, `az acr build`, `az containerapp job start` | Azure CLI token cache (`~/.azure`) | `az login` (CI: OIDC, see below) |
| Cloudflare API token | Reading the zone and Cloudflare's IP ranges, managing the `app` DNS record | Your password manager | `CLOUDFLARE_API_TOKEN` environment variable |
| Origin certificate PFX and its password | Application Gateway's HTTPS listener | A file outside the repo, e.g. `~/.secrets/biffkittz-origin.pfx` | `TF_VAR_tls_certificate_pfx_path`, `TF_VAR_tls_certificate_pfx_password` |
| Generated secrets (database passwords, JWT key) | The app and the bootstrap job | Key Vault (and the remote state) | Generated by Terraform; nobody handles them |

## Azure

### Sign in

Use the **Linux** Azure CLI inside WSL (see [DEVELOPMENT.md](DEVELOPMENT.md#1-install-the-tools)). The Windows CLI
also works through WSL interop, but it is slower and keeps its tokens on the Windows side.

```bash
az login                     # opens a browser; on a headless WSL use: az login --use-device-code
az account set --subscription 3c3f379f-8161-4631-a30c-a3af82622a6a
az account show --query "{subscription:name, id:id, user:user.name}" --output table
```

The azurerm provider and the azurerm state backend both pick up the CLI's token automatically. No client secret or
access key is involved, and `subscription_id` comes from `environments/demo.tfvars`. Tokens expire: if a plan fails
with `AADSTS700082` or "refresh token has expired", run `az login` again.

### Required permissions

| Scope | Role | Why |
| --- | --- | --- |
| Subscription | **Owner**, or **Contributor** + **Role Based Access Control Administrator** | Terraform creates resources *and* role assignments (AcrPull, Key Vault roles). Registering resource providers (`Microsoft.App`, …) also needs subscription-level rights |
| State storage account `demonstration` | See [Remote state](#remote-state) | Reading and writing `loginapp.terraform.tfstate` |

To keep Role Based Access Control Administrator narrow, add a condition that only allows the four roles this
configuration assigns: AcrPull, Key Vault Secrets User, Key Vault Secrets Officer and Key Vault Certificates Officer.
The portal's "Constrain roles" option builds that condition.

### What Terraform grants itself

Key Vault uses Azure RBAC, so even an Owner can't read or write secrets until a data-plane role is assigned.
The `key-vault` module grants the identity running Terraform two roles:

- **Key Vault Secrets Officer**;
- **Key Vault Certificates Officer**.

The identity is found with `data.azurerm_client_config.current.object_id`. The module then waits 90 seconds for the
assignment to propagate before creating secrets.

If someone else runs a later apply, Terraform adds the same roles for them. It also replaces the previous runner's
assignments, because the principal ID changed. For teams, prefer one CI identity that does all applies.

### Remote state

`backend.tf` stores state in blob `loginapp.terraform.tfstate`, in container `terraform` of storage account
`demonstration` (resource group `rg-terraform-state`). The backend takes a **blob lease** for every operation that can
write state, so concurrent applies are refused with "Error acquiring the state lock".

**Current setting: storage key.** `use_azuread_auth` is commented out, so the backend looks up the storage account
key with your Azure CLI identity. That needs `Microsoft.Storage/storageAccounts/listKeys/action` on the account,
which Owner, Contributor and Storage Account Contributor include.

**Recommended: Microsoft Entra ID.** No shared keys:

1. Grant every operator and CI identity **Storage Blob Data Contributor** on the `terraform` container (or the account):

   ```bash
   az role assignment create --role "Storage Blob Data Contributor" --assignee "$(az ad signed-in-user show --query id -o tsv)" \
     --scope "$(az storage account show -n demonstration -g rg-terraform-state --query id -o tsv)/blobServices/default/containers/terraform"
   ```

2. Uncomment `use_azuread_auth = true` (and `use_cli = true`) in `backend.tf`, then run
   `terraform init -reconfigure`.
3. Optionally, disallow shared key access on the account:
   `az storage account update -n demonstration -g rg-terraform-state --allow-shared-key-access false`.

**Protect the state.** It holds the generated passwords, the JWT signing key and the PFX, all marked sensitive but
readable by anyone who can read the blob. Treat access to the state like access to Key Vault:

- keep the container private;
- limit who has data roles;
- keep versioning and soft delete on.

**A stuck lock.** If an apply was killed and left the lock behind, the next run reports the lock ID. Use
`terraform force-unlock <LOCK_ID>`, but only once you're sure nobody else is running.

### Pushing images and running the bootstrap job

- **`az acr build`** builds in the registry and needs push rights. Owner and Contributor have them through the
  registry's ARM permissions; otherwise grant **AcrPush** on the registry.
- **`az containerapp job start`** needs `Microsoft.App/jobs/start/action`, which Contributor includes.

Starting a job is a privileged action. The Jobs API accepts an execution template that can override the job's image
and command, so anyone who can start the job can read the secrets it references, including the PostgreSQL
administrator password. Microsoft calls this out in its secrets documentation. Grant the permission only to people
who may hold that password.

### CI/CD with OpenID Connect

The included workflow (`.github/workflows/infra.yml`) runs only credential-free checks: formatting, validation,
linting and mocked tests. To plan or apply from GitHub Actions, use **OIDC workload identity federation**, so GitHub
never stores an Azure secret.

1. Create an identity for the pipeline and trust GitHub's token issuer for this repository's `demo` environment:

   ```bash
   az identity create --name id-loginapp-github --resource-group rg-terraform-state --location eastus
   az identity federated-credential create --name github-demo \
     --identity-name id-loginapp-github --resource-group rg-terraform-state \
     --issuer https://token.actions.githubusercontent.com \
     --subject repo:biffkittz/login-app:environment:demo \
     --audiences api://AzureADTokenExchange
   ```

2. Give it the same permissions a person needs: Owner (or Contributor + Role Based Access Control Administrator) on
   the subscription, and Storage Blob Data Contributor on the state container.
3. In the GitHub repository, create an environment `demo` (add required reviewers for applies). Add these variables:
   - `AZURE_CLIENT_ID`: the identity's client ID;
   - `AZURE_TENANT_ID`;
   - `AZURE_SUBSCRIPTION_ID`.

   Add these secrets: `CLOUDFLARE_API_TOKEN`, `TLS_CERTIFICATE_PFX_BASE64` and `TLS_CERTIFICATE_PFX_PASSWORD`.
4. In the job, request `permissions: id-token: write` and set `ARM_USE_OIDC=true`, `ARM_CLIENT_ID`, `ARM_TENANT_ID`
   and `ARM_SUBSCRIPTION_ID`. Add `use_oidc = true` and `use_azuread_auth = true` to the backend (or pass them with
   `-backend-config`). Write the PFX to a temporary file and point `TF_VAR_tls_certificate_pfx_path` at it.

## Cloudflare

### Create the API token

Use a scoped **API token**, not the account-wide Global API Key.

1. In the Cloudflare dashboard, open **My Profile → API Tokens → Create Token**, then pick the **Edit zone DNS**
   template.
2. Set **Permissions** to **Zone · DNS · Edit**.
3. Under **Zone Resources**, choose **Include · Specific zone · biffkittz.com**.
4. Optional but recommended:
   - **Client IP Address Filtering**: your public IP and CI's.
   - **TTL**: an expiry date, so a leaked token dies on its own.
5. Create it and copy the token once. Cloudflare doesn't show it again.

These permissions cover everything Terraform does:

- look up the zone ID for `biffkittz.com` (DNS Read is accepted for that);
- create, update and delete the single `app` A record.

Reading Cloudflare's IP ranges uses a public endpoint and needs no permission.

### Use the token

The provider reads `CLOUDFLARE_API_TOKEN` from the environment. It is deliberately **not** a Terraform variable, so
it can't end up in a tfvars file, a plan file or the state.

```bash
read -rsp 'Cloudflare API token: ' CLOUDFLARE_API_TOKEN && export CLOUDFLARE_API_TOKEN && echo
# Optional check: prints "This API Token is valid and active"
curl -s -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" https://api.cloudflare.com/client/v4/user/tokens/verify \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["messages"][0]["message"])'
```

To rotate the token, use **Roll** on the token in the dashboard, then update your password manager and the CI
secret.

### Zone settings to check once

Terraform manages only the `app` record. These zone-wide settings affect every record in `biffkittz.com`, so set
them in the dashboard:

| Setting | Value | Why |
| --- | --- | --- |
| SSL/TLS → Overview → encryption mode | **Full (strict)** | Cloudflare connects to the gateway over HTTPS and verifies the origin certificate. *Flexible* would use plain HTTP, which the gateway doesn't accept |
| SSL/TLS → Edge Certificates → Always Use HTTPS | On | Visitors who type `http://` are redirected at the edge |
| SSL/TLS → Edge Certificates → Minimum TLS Version | 1.2 | Matches the gateway's policy |
| SSL/TLS → Edge Certificates → HSTS | Optional | Add it once HTTPS works end to end; it is hard to undo, because browsers cache it |

## The origin certificate (PFX)

The gateway presents a **Cloudflare Origin CA** certificate. Cloudflare trusts it when validating the origin;
browsers don't, which is fine, because browsers only ever see Cloudflare's edge certificate.

1. **Create it.** In the dashboard for `biffkittz.com`, open **SSL/TLS → Origin Server → Create Certificate**:
   - **Generate private key and CSR with Cloudflare**, with an RSA (2048) key;
   - host names `*.biffkittz.com` and `biffkittz.com`;
   - a validity of up to 15 years.

   Copy the certificate into `origin.pem` and the private key into `origin.key`. The key is shown only once.

2. **Convert to PFX.** Application Gateway needs a password-protected PKCS#12 file with the private key:

   ```bash
   mkdir -p ~/.secrets && chmod 700 ~/.secrets
   read -rsp 'New PFX password: ' PFX_PASSWORD && export PFX_PASSWORD && echo
   openssl pkcs12 -export -inkey origin.key -in origin.pem \
     -out ~/.secrets/biffkittz-origin.pfx -passout env:PFX_PASSWORD
   chmod 600 ~/.secrets/biffkittz-origin.pfx
   shred -u origin.key            # the PFX now holds the key
   ```

   If you already have the wildcard PFX, just copy it to `~/.secrets/`. OpenSSL 3 encrypts PFX files with AES-256 by
   default. If Key Vault rejects the import with a password or format error, re-create the file with `-legacy`
   added to the `openssl pkcs12` command.

3. **Give it to Terraform** in the shell where you run it:

   ```bash
   export TF_VAR_tls_certificate_pfx_path=~/.secrets/biffkittz-origin.pfx
   export TF_VAR_tls_certificate_pfx_password="$PFX_PASSWORD"
   ```

Terraform imports the file into Key Vault as `app-biffkittz-com-origin`. Every plan reads the file, so keep it
available. Changing the file and applying imports a new version, and the gateway switches to it on its own. The repo's
`.gitignore` blocks `*.pfx`, `*.pem` and `*.key` as a safety net, but keep these files outside the repository
anyway.

## Handling secrets

**Do:**

- Keep the Cloudflare token, the PFX and its password in a password manager, and load them per shell session with
  `read -s` as shown above.
- Treat the remote state as secret, and use Entra ID authentication for it.
- Let workloads read secrets only from Key Vault, through their managed identities.

**Don't:**

- Commit any `*.tfvars` other than `environments/*.tfvars`, and never put a secret in those.
- Pass secrets with `-var` on the command line: they end up in shell history.
- Share saved plan files (`*.tfplan`). They contain the same secrets as the state, and `.gitignore` excludes them.
